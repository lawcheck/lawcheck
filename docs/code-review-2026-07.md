## Блок 1 — деньги и доступ

### 🔴 1. Платный отчёт открывается любому посетителю по ссылке из публичной ленты

`lawcheck/web/routes.py:566` — `_unlock_order_id` определяет доступ так:

```python
oid = await asyncio.to_thread(repo.paid_order_id_for_scan, scan.id)
```

То есть право на платный контент привязано **к скану**, а не к покупателю.
`paid_order_id_for_scan` (`db/repo.py:82`) возвращает любой оплаченный заказ по этому
скану, кем бы он ни был оформлен.

Главная страница публикует ссылки на 10 последних сканов
(`routes.py:112` → `templates/index.html:118`). Фильтр ленты (`routes.py:106`) отсеивает
только домены со «взрослыми» и игорными подстроками — про оплату он ничего не знает.

**Сценарий:** клиент оплачивает отчёт по своему скану → скан попадает в ленту на главной →
любой посетитель открывает `/report/{scan_id}` и получает полный отчёт с рецептами
«Как исправить», а также `/report/{scan_id}/documents` (черновик Политики ПДн под сайт
клиента) и `/report/{scan_id}/rkn-notification`. Оба эндпоинта пускают по тому же
`_unlock_order_id` (`routes.py:580`, `routes.py:592`).

Это одновременно потеря выручки и раскрытие документов, сгенерированных для клиента.

**Чинить:** доступ выдавать покупателю (сессия аккаунта или токен заказа в ссылке),
а не факту оплаты скана. Плюс исключить из ленты сканы, по которым есть заказ.

### 🔴 2. Подписка Pro не истекает — ✅ ИСПРАВЛЕНО (ветка `fix/subscription-expiry`)

`db/repo.py:457`:

```python
def user_has_paid_order(user_id: int) -> bool:
    """Есть ли у пользователя оплаченный заказ (активная Pro-подписка)."""
```

Проверяется только факт `status == "paid"`, без даты. У модели `Order`
(`db/models.py:111`) нет ни поля срока, ни признака периода — есть только `paid_at`.

Разовая оплата 990 ₽ открывает Pro навсегда. При этом тариф продаётся как
ежемесячный (990 ₽/мес), и еженедельный мониторинг тоже завязан на `status == "paid"`
(`routes.py:329`, `routes.py:367`).

**Чинить:** поле `paid_until` в `Order` (или отдельная сущность подписки) и проверка
по текущей дате во всех местах, где сейчас смотрят `status == "paid"`.

### 🟠 3. `create_payment` молча возвращает пустую платёжную ссылку

`payments/tochka.py:69`:

```python
return PaymentLink(
    operation_id=data.get("operationId", ""),
    url=data.get("paymentLink", ""),
)
```

`raise_for_status()` ловит только HTTP-ошибки. Если банк ответил 200 с другой
структурой (а в шапке файла прямо написано, что имена полей выверены лишь по
документации и ждут проверки боевым платежом), пользователь получает редирект на
пустой URL, а заказ сохраняется с пустым `operation_id`.

Дальше это уже не чинится: `pay_success` (`routes.py:246`) проверяет оплату только
`if o and o.operation_id`. Клиент заплатил — доступ не открылся.

**Чинить:** при пустом `operationId` или `paymentLink` поднимать исключение.

### 🟠 4. `is_paid` перехватывает слишком узкий класс ошибок

`payments/tochka.py:88`:

```python
except httpx.HTTPError as e:
```

`r.json()` на не-JSON ответе бросит `json.JSONDecodeError`, а `ops[0]` при неожиданной
структуре — `IndexError`/`AttributeError`. Ни то, ни другое не наследует `httpx.HTTPError`.
Результат — 500 на `/webhooks/tochka` (банк будет ретраить) и 500 на `/pay/success`
у клиента, только что заплатившего деньги, вместо честного «оплата не подтверждена».

### 🟠 5. Статус `AUTHORIZED` считается оплатой

`payments/tochka.py:24`:

```python
_PAID_STATUSES = {"APPROVED", "AUTHORIZED"}  # APPROVED — списание прошло
```

Комментарий сам говорит, что списание — это `APPROVED`. `AUTHORIZED` — деньги
захолдированы, но не списаны, и холд может не завершиться. Сейчас доступ выдаётся
до фактического получения денег.

Если это осознанный компромисс — стоит записать причину рядом; если нет — убрать
`AUTHORIZED` из множества.

### 🟠 6. Нет ограничения частоты на регистрацию, вход и сброс пароля

`web/auth.py:76`, `:103`, `:176` — ни на одном нет лимита.

- `/register` отправляет письмо подтверждения на **любой** введённый адрес
  (`auth.py:94`). Это готовый инструмент рассылки с твоего домена по чужим адресам:
  бьёт по репутации почты (Timeweb на домене) и по доставляемости писем клиентам.
- `/login` — неограниченный перебор пароля.
- `/forgot-password` — неограниченная отправка писем существующим пользователям.

**Чинить:** лимит по IP и по email, хотя бы простой счётчик в Redis (он уже в стеке).

### 🟡 7. Сброс пароля не завершает остальные сессии

`web/auth.py:209` — `deps.logout_user(request)` очищает только сессию текущего запроса.
Если аккаунт увели, смена пароля не выкидывает злоумышленника: его cookie продолжает
работать, потому что в сессии лежит только `uid`.

**Чинить:** версия сессии (поле `session_epoch` у пользователя, сверяется в `current_user`).

### 🟡 8. `order_id` утекает через Referer и историю браузера

`/account/{order_id}` (`routes.py:298`) — capability-URL без аутентификации: кто знает
id, тот и владелец заказа. Решение осознанное (кабинет без регистрации), но id лежит
в пути URL, а на страницах подключена Яндекс.Метрика — путь уходит третьей стороне.
Плюс история браузера и пересылка ссылки.

**Чинить:** как минимум `Referrer-Policy: no-referrer` на `/account/*`; надёжнее —
токен в фрагменте или обмен ссылки на cookie-сессию при первом заходе.

### 🟡 9. Логин выдаёт существование email по времени ответа

`web/auth.py:107` — при отсутствии пользователя `verify_password` не вызывается, argon2
не считается, ответ возвращается заметно быстрее. `/forgot-password` от перечисления
защищён явно и с комментарием (`auth.py:179`), а вход — нет. Непоследовательно.

**Чинить:** считать argon2 по фиктивному хешу, когда пользователь не найден.

### ⚪ 10. Внутренний ключ сравнивается небезопасно

`routes.py:380` — `request.headers.get("X-Internal-Key") != settings.internal_key`.
Обычное сравнение строк. Заменить на `secrets.compare_digest`.

### ⚪ 11. `_valid_email` пропускает мусор

`web/auth.py:27` — `"@" in email and "." in email.split("@")[-1]`. Пройдёт `a b@c.d`
и `@@@.x`. На доставляемость влияет мало, но мусор в базе копится.

### ⚪ 12. Гонка в `mark_order_paid` даёт дубли уведомлений

`db/repo.py:105` — read-modify-write без блокировки. Вебхук и `/pay/success` могут
сработать одновременно и оба получить `True` → два одинаковых сообщения в Telegram.
Ущерба нет, но раздражает.

### ⚪ 13. Вебхук Точки — бесплатный способ нагрузить чужой API

`routes.py:464` — подпись JWT не проверяется намеренно и это правильно: статус
перепроверяется авторизованным запросом к банку. Но эндпоинт открыт, и каждый POST
с валидным на вид `operationId` порождает исходящий запрос к API Точки.

**Чинить:** лимит частоты на эндпоинт.

## Блок 2 — внешний ввод (краулер, вебхуки)

### 🔴 14. SSRF: краулер ходит по любому URL, включая внутреннюю сеть Docker

`web/routes.py:519` — единственная проверка адреса:

```python
if not url.startswith(("http://", "https://")):
    url = "https://" + url
```

Дальше URL уходит в краулер, который открывает его Chromium'ом
(`crawler/browser.py`) или качает через httpx (`crawler/pdf_fetcher.py`). Ни там,
ни там нет запрета на приватные адреса.

Краулер работает **внутри** сети Docker Compose, рядом с `postgres`, `redis`, `api`
и `caddy`. Значит доступны `http://api:8000/...`, `http://127.0.0.1:8000/...`,
`10.x`, `169.254.169.254` и прочее, что снаружи закрыто.

Самая неприятная цель — `/inbox` (`routes.py:163`). В коде маршрута защиты нет,
и это зафиксировано его же докстрингом:

```python
"""Входящие: вопросы чат-виджета + email-лиды. Защита — basic_auth на Caddy."""
```

Запрос `http://api:8000/inbox` идёт мимо Caddy, а с ним и мимо basic_auth. Страница
отдаёт до 200 заявок и 200 лидов с email-адресами. Текст загруженных страниц
складывается в снапшот и сохраняется в БД; часть попадает в `evidence` находок,
которые видны в отчёте.

Побочно: `_registered_domain` (`crawler/crawler.py:47`) для хоста без публичного
суффикса возвращает сам хост (`api` → `api`), поэтому краулер спокойно ходит по
ссылкам внутри такого «домена».

**Чинить:** резолвить хост до запроса и отклонять loopback/private/link-local
диапазоны — и повторять проверку на каждом редиректе, иначе обход тривиален.
Отдельно: продублировать защиту `/inbox` в приложении, не полагаясь на прокси
(защита на одном слое = отсутствие защиты, когда запрос приходит с другой стороны).

### 🟠 15. `max_pages` в веб-форме не ограничен

`web/routes.py:520` — `max_pages: int = Form(10)`, верхней границы нет.
В API-схеме она есть: `Field(None, ge=1, le=100)` (`api/schemas.py:6`).

То есть публичный HTML-путь защищён слабее внутреннего API. `POST /scan` с
`max_pages=1000000` займёт воркер до упора в `job_timeout=600`.

### 🟠 16. Нет ограничения частоты на запуск сканов

Ни `/scan` (форма), ни `POST /scan` (API) не ограничены. Последствия шире, чем
нагрузка: сервис краулит **чужие сайты с твоего IP**, поэтому abuse-жалобы за
чужой краулинг придут на твой VPS и твой домен.

### 🟡 17. Очередь краулера растёт без ограничения

`crawler/crawler.py:117` — все ссылки страницы кладутся в `queue`, дедуп только по
`visited`, а сама очередь не ограничена и пересортировывается на каждой итерации
(`queue.sort` внутри `while` — O(n² log n) на больших сайтах).

Плюс URL с разными query-параметрами считаются разными страницами, поэтому
календари, фильтры и пагинация съедают бюджет страниц вместо Политики и контактов.

### 🟡 18. Глобальная подмена `socket.getaddrinfo` бьёт по всем исходящим

`net.py:54` — `force_ipv4()` меняет резолвер **на весь процесс**: краулер, клиенты
РКН и ЕГРЮЛ, SMTP. Всё принудительно IPv4.

Отдельно `_tg_ip_cache` (`net.py:21`) пиннит адрес Telegram навсегда, без TTL: если
выбранный IP перестанет отвечать, процесс будет долбиться в него до рестарта.
Причина решения задокументирована и понятна ([[telegram-bot-egress-ru-dc]]), но
кеш стоит сделать протухающим.

Общее впечатление: **это самая аккуратная часть проекта.** Все 66 находок
создаются с `law_reference`, `TODO`/`FIXME` нет ни одного, широкий `except` ровно

Замечания ниже — про краевые случаи, а не про юридическую логику.

### 🟠 19. Ограничение нашего краулера превращается в претензию к сайту клиента

`pd_152/policy_validity.py:30`:

```python
if page is None:
    return [Finding(..., severity=Severity.WARNING,
                    evidence="Не удалось загрузить документ Политики ...")]
```

`page is None` означает «страницы нет в снапшоте». Но её может не быть просто
потому, что краулер до неё не дошёл: дефолт формы — 10 страниц (`routes.py:520`),
а Политика приоритезируется, но конкурирует с остальными ссылками.

В юридическом отчёте это выглядит как замечание в адрес клиента, хотя причина —
наш бюджет обхода. Ровно тот класс ложных срабатываний, который запрещён правилом
в `lawcheck/checks/CLAUDE.md`.

**Чинить:** различать «ссылка есть, но страницу не обходили» (находку не выдавать)
и «обходили, не открылась» (выдавать).

### 🟡 20. A2 проверяет только первую ссылку на Политику

`pd_152/policy_validity.py:27` — `policy_url = links[0][1]`. Если на сайте несколько
ссылок (устаревшая в футере и актуальная на отдельной странице), проверяется
произвольная первая, и вывод зависит от порядка обхода.

**Чинить:** проверять все найденные и брать лучший результат, а расхождение между
ними само по себе стоит показать клиенту.

### 🟡 21. `MIN_TEXT_LEN = 1500` — порог без обоснования

`pd_152/policy_validity.py:14`. Политика в 1499 символов получает WARNING
«слишком короткая». Это утверждение в юридическом документе, за ним должна стоять
причина, а её в коде нет.

Остальные пороги и маркеры живут в YAML (`dictionaries/`), а этот — в коде.

### ⚪ 22. Единственный широкий `except` в ядре

`advertising/_ad_signs.py:29` — `except Exception` вокруг `urlparse`/`parse_qs`.
Сузить до `ValueError`.

## Блок 4 — отчёты, БД, уведомления

### 🟠 23. Неэкранированный email ломает уведомление об оплате

`web/routes.py:250` и `:483`:

```python
f"Покупатель: <b>{o.email or 'email не указан'}</b>"
```

Уходит в `telegram.send_message` с `parse_mode: "HTML"` (`notify/telegram.py:33`).
Email приходит от пользователя и не экранируется. Символ `<` в адресе → Telegram
отвечает 400 → `except Exception: log.warning` (`telegram.py:40`) глушит ошибку.

Итог: **оплата прошла, а уведомления о ней нет** — и узнаешь ты об этом только из
логов, если полезешь смотреть.

**Чинить:** `html.escape` для всех пользовательских данных в сообщениях бота.
В генераторах документов это уже сделано правильно (`reporting/policy_draft.py:32`,
`rkn_notification_draft.py:21`, `followup.py:150`) — здесь просто забыли.

### 🟡 24. Слабая валидация email пропускает переводы строки

`web/auth.py:27`:

```python
return "@" in email and "." in email.split("@")[-1]
```

Строка `"a@b.ru\nBcc: victim@example.com"` эту проверку проходит: `@` есть,
точка в последнем сегменте есть. `email.strip()` убирает только края.

Дальше значение уходит в `msg["To"] = to` (`notify/mailer.py:31`). Современная
политика `email.message` скорее всего отвергнет заголовок с переводом строки, но
закладываться на это не стоит — валидация адреса должна отсекать это сама.

**Чинить:** нормальная проверка адреса с явным запретом управляющих символов.
Это же снимает пункт про мусор в базе.

### ⚪ 25. `blog_article.html` рендерит HTML без экранирования

`templates/blog_article.html:28` — `{{ article.html|safe }}`. Источник — твои
собственные markdown-файлы блога, не пользовательский ввод, поэтому сейчас
безопасно. Стоит держать в голове, если появятся внешние авторы.
